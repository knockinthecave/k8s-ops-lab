# 06. CI 매니페스트 검증

> 로컬 검증과 GitHub Actions 실행(통과, 일부러 실패시킨 PR)까지 확인했다.

## 1. 목표

잘못된 매니페스트가 클러스터에 닿기 전에 PR 단계에서 막히게 한다. 이 저장소에는 직접 빌드하는 앱이 없고(podinfo 공개 이미지만 사용) 그래서 **이미지 빌드·푸시는 하지 않는다.** 대신 매니페스트 검증과 보안 스캔에 집중한다.

## 2. 구성

| 파일 | 역할 |
| --- | --- |
| `scripts/ci-check.sh` | 실제 검사. 로컬과 CI가 같은 스크립트를 쓴다 |
| `.github/workflows/ci.yaml` | PR과 `main` 푸시에서 위 스크립트 실행 |
| `.yamllint.yaml` | yamllint 설정 (`relaxed` 기반, 줄 길이 검사 끔) |

| 단계 | 도구 | 실패 시 |
| --- | --- | --- |
| 1 | yamllint 1.38.0 | 차단 |
| 2 | kubeconform v0.8.0 (`-strict`) | 차단 |
| 3 | trivy 0.76.2 `config` | CRITICAL만 차단, HIGH 이하는 보고만 |
| 4 | trivy `image` (podinfo 이미지) | 보고만 |

- 도구 버전은 워크플로 `env`에 고정했다.
- kubeconform 대상은 쿠버네티스 리소스 파일만이다. helm values(`*-values.yaml`)와 kind 설정(`cluster/kind.yaml`)은 리소스가 아니라서 제외했다.
- ServiceMonitor, PrometheusRule 같은 CRD는 커뮤니티 스키마 카탈로그(`datreeio/CRDs-catalog`, `main` 브랜치)에서 가져온다. **버전이 고정되지 않은 외부 의존**이다.
- 클러스터는 v1.37이지만 kubeconform 스키마는 `1.34.0`으로 검증한다(`K8S_VERSION`으로 바꿀 수 있음). 1.37 스키마가 있는지는 확인하지 않았다.

## 3. 실습 결과 (로컬 실행)

### 현재 저장소 상태
- yamllint, kubeconform: 통과 (14개 리소스 모두 Valid).
- trivy config: HIGH 3건, CRITICAL 0건. 전체로는 14건(LOW 7, MEDIUM 4, HIGH 3). 모두 `apps/podinfo/deployment.yaml`에 `securityContext`가 없어서 나온다(root 허용, 읽기 전용 루트 파일시스템 아님, seccomp 미지정 등).
- trivy image (`podinfo:6.17.0`, 수정 버전이 있는 HIGH/CRITICAL만): HIGH 2종, CRITICAL 0. 둘 다 이미지에 포함된 Go 라이브러리다(`go-jose` 1건, `golang.org/x/net` 1건이고 후자는 `podcli` 바이너리에도 있음).

### 일부러 망가뜨려서 막히는지 확인
저장소를 복사한 사본에서 하나씩 망가뜨리고 `ci-check.sh`를 돌렸다. 4건 모두 exit 1이었다.

| 변경 | 막은 단계 | 메시지 요지 |
| --- | --- | --- |
| HPA `minReplicas` → `minReplica` 오타 | kubeconform | `additional properties 'minReplica' not allowed` |
| Service `port: 9898` → `"abc"` | kubeconform | `got string, want integer` |
| PrometheusRule `expr` → `exp` 오타 | kubeconform | `missing property 'expr'`, `additional properties 'exp' not allowed` |
| YAML 문법 오류(닫히지 않은 `[`) | yamllint | 1단계에서 중단 |

- `-strict` 덕에 오타(없는 필드)도 잡힌다. 없으면 모르는 필드는 무시된다고 알고 있다.
- CRD도 카탈로그에 스키마가 있어서 CRD 필드 오타까지 잡혔다.

### GitHub Actions에서 확인
- 정상 PR(#5): `validate` 통과, 18초. 로컬과 같은 결과(Valid 14, trivy config HIGH 3, image HIGH 2종).
- HPA 필드 오타를 넣은 일회용 PR(#6): `validate` 실패, 11초. 로그에 `additional properties 'minReplica' not allowed`가 나왔다. PR 체크에서 `fail`로 표시됐고 확인 후 닫고 브랜치를 지웠다.
- 같은 PR에 GitGuardian 체크도 자동으로 붙어 있었다(이 워크플로와 별개).

## 4. 판단 기록

- **보안 스캔을 전부 차단으로 두지 않은 이유**: 지금 `main`이 HIGH 3건으로 바로 실패하기 때문이다. 처음부터 막으면 CI가 빨갛게 고정되어 신호로서 의미를 잃는다. 그래서 새로 생기는 CRITICAL만 막고, HIGH 이하는 로그에 남긴다. `securityContext` 보강은 13, 14번에서 다룬다.
- **이미지 스캔을 차단하지 않은 이유**: 취약점은 우리가 고칠 수 없는 외부 이미지(podinfo) 안에 있고, 새 CVE가 생기면 코드를 안 바꿔도 CI가 깨질 수 있다. 차단하려면 정기 스케줄 실행과 예외 관리가 필요하다.
- **스크립트로 분리한 이유**: 워크플로 YAML에 명령을 흩어 두면 로컬에서 재현이 어렵다. 같은 스크립트를 쓰면 CI가 실패했을 때 로컬에서 똑같이 돌려 볼 수 있다.

## 5. 배운 점

- 매니페스트 검증은 클러스터 없이 PR 단계에서 된다. `kubectl apply --dry-run`은 클러스터 접근이 필요하다고 알고 있어서, CI에는 스키마 기반의 kubeconform이 맞다.
- 스캔을 켜자마자 **우리 매니페스트의 실제 문제**가 나왔다(`securityContext` 없음). "동작한다"와 "안전하다"는 다르다.
- 이미지 스캔에서도 실제 HIGH 취약점이 나왔고, 이는 바로 고칠 수 없는 외부 의존이다. 막을지 알릴지를 정하는 것이 도구 설정보다 어려운 부분이다.
- 도구가 요구하는 입력의 범위를 맞춰야 한다. 대시보드 JSON이 섞인 폴더를 통째로 넘기자 `missing 'kind' key` 오류가 났다.

## 6. 검증하지 않은 것

- trivy DB 다운로드가 레이트 리밋에 걸리는 경우 (이번 두 번의 실행에서는 문제없었다)
- 브랜치 보호 규칙으로 CI 통과를 머지 조건으로 강제하는 것 (설정하지 않음)
- CRD 스키마 카탈로그가 바뀌거나 접근 불가일 때의 동작
- 쿠버네티스 1.37 스키마로 검증하는 것
- GitHub Actions를 커밋 SHA로 고정하는 것(현재 `actions/checkout@v4` 태그)
