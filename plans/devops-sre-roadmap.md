# DevOps/SRE 실습 로드맵

> 상태: **초안 (검토 대기)**. 이 문서를 검토하고 확정한 뒤에 실습을 시작한다.
> 작성일: 2026-11-16

## 1. 목적과 원칙

**목적**: DevOps/SRE 직무에서 실제로 하는 일을 로컬 환경에서 재현하고, 그 과정을 면접에서 설명할 수 있는 기록으로 남긴다. 자격증(CKA)과는 별개로, 실무 연관성을 기준으로 항목을 고른다.

**원칙**

1. **깨뜨리고 고친다.** 설정을 넣는 데서 끝내지 않고, 장애를 일으켜서 감지, 진단, 복구까지 해 본다.
2. **변경은 Git에 남긴다.** `kubectl set`처럼 Git에 남지 않는 변경은 실습 후 반드시 파일 기준으로 되돌린다(01번의 교훈). GitOps 단계 이후에는 클러스터를 직접 수정하지 않는 것을 기본으로 한다.
3. **검증한 것과 아는 것을 구분해서 쓴다.** 직접 재현한 내용만 "결과"에 적고, 일반 지식은 "참고" 또는 "아직 검증하지 않은 것"으로 분리한다(01, 02번에서 지켜 온 방식).
4. **운영 관점으로 쓴다.** 설정 나열이 아니라 "무엇이 위험했고, 어떻게 감지했고, 어떻게 막았는가"를 쓴다.
5. **재현 가능해야 한다.** 매니페스트, helm values, 알림 규칙은 모두 파일로 저장하고 차트·이미지 버전을 고정한다.

## 4. 단계별 계획

우선순위: **[필수]** 직무 핵심, **[권장]** 면접에서 자주 나오거나 실무 빈도가 높음, **[선택]** 시간이 되면.
규모: S(반나절 이내), M(하루 안팎), L(며칠).

### Phase A. 관측성과 인시던트 대응

**03. 메트릭 수집과 대시보드** [필수] M
- 내용: metrics-server 설치(`kubectl top`), `kube-prometheus-stack`(Prometheus, Grafana, Alertmanager, kube-state-metrics) helm 설치
- 해 볼 것: podinfo 지표 쿼리(PromQL), 02번의 `oom-test`, `cpu-test`를 다시 띄워 재시작 횟수와 CPU throttling이 지표로 어떻게 보이는지 확인, 대시보드 구성
- 확인할 것: kubelet의 probe 관련 지표가 실제로 나오는지, 어떤 지표가 어떤 증상을 보여 주는지
- 산출물: `monitoring/` (helm values, 대시보드 JSON), 실습 문서

**04. 알림과 로깅** [필수] M
- 내용: PrometheusRule로 알림 규칙 작성(재시작 반복, throttling 과다, 파드 NotReady 지속), Alertmanager 라우팅, 로그 수집(Loki + Alloy 또는 Promtail)
- 해 볼 것: 장애를 일으켜 알림이 실제로 발화하는지, 알림 → 대시보드 → 로그로 이어서 원인을 찾는 흐름
- 확인할 것: 알림이 너무 시끄럽거나(오탐) 너무 늦는 경우(미탐)의 조정
- 산출물: 알림 규칙 파일, 알림 설계 기준(무엇을 왜 알리는가)

**05. 장애 진단 훈련 (포스트모템)** [필수] M
- 방식: 계획자(Claude)가 문제를 심고 **증상만 알려 주면** 직접 원인을 찾는다. 답은 해결 후에 공개한다.
- 시나리오 후보: 이미지 태그 오타, 잘못된 probe 경로, 리소스 부족으로 `Pending`, Service 셀렉터 불일치, ConfigMap 키 오타, liveness가 의존성을 검사해서 연쇄 재시작, `readinessProbe` timeout, `startupProbe` 실패, DNS 문제, 노드 NotReady
- 기록: **포스트모템 형식**(증상, 영향, 감지 방법, 원인, 해결, 재발 방지, 타임라인) + 반복되는 진단은 **런북**으로 정리
- 산출물: `docs/postmortems/`, `docs/runbooks/`

### Phase B. 가용성

**06. 가용성 설계** [필수] L
- 내용: PodDisruptionBudget, 노드 `drain`, `topologySpreadConstraints`, HPA(CPU/메모리 기반, 이후 커스텀 지표), ResourceQuota, LimitRange, PriorityClass
- 해 볼 것: PDB 없이 drain했을 때 요청이 끊기는지 vs PDB 적용 후, `minAvailable`을 replicas와 같게 두어 drain이 멈추는 경우, 한 노드 장애 시 파드 분산 효과, 부하를 주었을 때 HPA 동작과 스케일 지연
- 산출물: 관련 매니페스트, 부하 중 지표 캡처

### Phase C. 배포 자동화와 GitOps

**07. CI와 이미지 파이프라인** [필수] M
- 내용: GitHub Actions로 매니페스트 린트(kubeconform 등), 이미지 빌드·푸시(GHCR), 이미지 취약점 스캔(Trivy), Helm/Kustomize 정리
- 해 볼 것: PR에서 잘못된 매니페스트가 CI에서 막히는지, 취약점 스캔 결과 확인
- 판단 필요: podinfo는 공개 이미지를 쓰고 있으므로 직접 빌드할 작은 앱이 필요한지 (질문 3 참고)

**08. GitOps 기본: Argo CD** [필수] L
- 내용: Argo CD 설치, 이 저장소를 소스로 Application 등록, 자동 동기화, self-heal, prune
- 해 볼 것:
  - 클러스터를 `kubectl`로 직접 수정하면 드리프트가 감지되고 되돌려지는지 (01번의 "Git에 안 남는 변경" 문제의 해결)
  - Git에 잘못된 변경을 푸시했을 때 동작과 롤백(`git revert`)
  - app-of-apps 또는 ApplicationSet으로 여러 앱 관리
  - 동기화 실패 시 진단
- 산출물: `gitops/` 구조, Application 매니페스트, 실습 문서

**09. GitOps: Flux** [권장] L
- 내용: Flux(GitRepository, Kustomization, HelmRelease) 설치, 같은 앱을 Flux로 배포
- 해 볼 것: Argo CD와 **같은 시나리오**(드리프트, 잘못된 푸시, 롤백)를 반복해서 차이를 비교. 이미지 자동 업데이트(Image Automation) 확인
- 주의: Argo CD와 Flux를 같은 클러스터에서 같은 리소스에 쓰면 충돌하므로 **별도 kind 클러스터** 또는 별도 네임스페이스·경로로 분리한다.

**10. GitOps 비교와 운영 설계** [권장] S
- 내용: Argo CD vs Flux 비교표(구조, UI, 멀티 클러스터, 권한, 알림, 학습 곡선), 저장소 구조 설계(환경 분리: dev/staging/prod, 모노레포 vs 멀티 레포), 시크릿 처리 방침
- 산출물: 비교 문서, 의사결정 기록(ADR)

**11. 점진적 배포** [권장] M
- 내용: Argo Rollouts로 카나리와 블루/그린, 지표 기반 자동 분석과 자동 롤백(03번의 Prometheus 연계)
- 해 볼 것: 에러율이 높은 버전을 카나리로 배포했을 때 자동으로 롤백되는지

### Phase D. SRE 실천

**12. SLI/SLO와 에러 버짓** [필수] M
- 내용: podinfo의 SLI 정의(가용성, 지연), SLO 설정, 에러 버짓 계산, 번레이트 알림(빠른/느린 윈도우)
- 해 볼 것: 장애를 일으켜 에러 버짓이 소진되는 모습을 대시보드로 보고, 번레이트 알림이 발화하는지 확인
- 산출물: SLO 문서, 규칙 파일

**13. 부하·카오스 테스트** [권장] M
- 내용: k6로 부하 테스트, Chaos Mesh 또는 Litmus로 파드 삭제, 네트워크 지연, 노드 장애 주입
- 해 볼 것: 12번의 SLO가 지켜지는지 검증, 게임데이(미리 계획한 장애 시나리오를 팀처럼 순서대로 수행) 형식으로 기록

### Phase E. 보안과 네트워크

**14. 설정과 시크릿, 접근 제어** [필수] M
- 내용: ConfigMap/Secret 다루기, GitOps에서 시크릿을 안전하게 관리하는 방법(Sealed Secrets 또는 SOPS 또는 External Secrets 중 선택), RBAC(ServiceAccount, Role, RoleBinding), Pod Security Standards
- 해 볼 것: 권한이 없을 때의 에러를 일부러 만들고 `kubectl auth can-i`로 진단

**15. 네트워크 정책과 정책 엔진** [권장] M
- 내용: NetworkPolicy, Kyverno 또는 OPA Gatekeeper로 정책 강제(예: limit 없는 파드 거부, `latest` 태그 금지), 이미지 서명(cosign) 확인은 선택
- **주의**: kind의 기본 CNI(kindnet)는 NetworkPolicy를 강제하지 않는 것으로 알고 있다. 이 실습은 Calico나 Cilium으로 CNI를 바꾼 클러스터가 필요할 수 있다(기존 클러스터 재생성 필요). 착수 전에 확인한다.

**16. Ingress/Gateway API와 TLS** [권장] M
- 내용: 외부 트래픽 진입 구성, cert-manager로 TLS 인증서 자동화, 호스트·경로 기반 라우팅
- 판단 필요: Ingress 컨트롤러와 Gateway API 구현체 중 무엇을 쓸지. 일부 Ingress 컨트롤러는 유지보수 상태가 바뀌었다는 소식이 있어, 착수 시점의 최신 상태를 확인하고 정한다.

### Phase F. 클러스터 운영과 클라우드

**17. 클러스터 운영** [권장] L
- 내용: etcd 백업과 복구, 클러스터 업그레이드 절차(버전 스큐, 노드 하나씩 cordon/drain), StatefulSet과 PV/PVC, Velero로 백업·복구
- 해 볼 것: 백업에서 복구해 데이터가 돌아오는지, 업그레이드 중 서비스 영향
- 주의: kind에서 업그레이드는 제한적이어서 재현 방식(다른 버전 노드 이미지로 클러스터 구성 등)을 착수 시 검토한다.

**18. IaC와 클라우드** [권장] L
- 내용: Terraform으로 클러스터와 네트워크 구성, 관리형 쿠버네티스(EKS 또는 GKE)에 같은 앱 배포, 로컬과의 차이(LoadBalancer, 스토리지 클래스, IAM 연동, 비용)
- 주의: **비용이 발생할 수 있다.** 무료 크레딧과 예산 알림을 먼저 설정하고, 실습 후 반드시 리소스를 삭제한다(삭제 확인 절차를 문서에 포함).

### Phase G. 종합

**19. 캡스톤** [필수] M
- 내용: CI → GitOps 배포 → 관측성 → 알림 → 장애 주입 → 진단 → 포스트모템까지 전 과정을 하나의 시나리오로 연결해 게임데이로 수행
- 산출물: 전체 구조도, 최종 README, 면접용 요약(무엇을 만들었고 어떤 장애를 어떻게 다뤘는가)

## 5. 권장 진행 순서

```
03 메트릭 → 04 알림·로깅 → 05 장애 진단
    → 06 가용성
    → 07 CI → 08 Argo CD → 09 Flux → 10 비교
    → 11 점진적 배포
    → 12 SLO → 13 부하·카오스
    → 14 시크릿·RBAC → 15 네트워크 정책·정책 엔진 → 16 Ingress·TLS
    → 17 클러스터 운영 → 18 IaC·클라우드
    → 19 캡스톤
```

의존 관계:
- 04, 05, 11, 12는 03의 지표에 의존한다. 03이 가장 먼저다.
- 11(점진적 배포)은 08(Argo CD)과 03에 의존한다.
- 12(SLO)는 03, 04에 의존하고, 13의 검증 기준이 된다.
- 08, 09는 07에서 정리한 저장소 구조와 CI에 의존한다. 단, 07을 건너뛰고 08을 먼저 해도 된다(순서 조정 가능).
- 15의 NetworkPolicy는 CNI 교체가 필요할 수 있어 클러스터 재생성이 필요하다. 17(업그레이드 재현)도 클러스터 재구성이 필요할 수 있으므로, 클러스터를 새로 만드는 실습(15, 17)은 가능하면 모아서 한 번에 한다.

**최소 코어 (시간이 부족할 때)**: 03, 04, 05, 06, 08, 12, 14, 19

- GitOps 단계(08 이후)에서 `apps/`와 `gitops/`의 관계가 바뀔 수 있으므로 **지금 구조를 확정하지 않고 08 착수 시 재검토**한다.

## 7. 기록 형식

**실습 문서** (`docs/labs/NN-*.md`): 목표, 적용한 설정, 실습(명령과 결과), 배운 점, 자주 만나는 문제, 다음 단계. 직접 확인한 것과 일반 지식을 구분한다.

**포스트모템** (`docs/postmortems/`): 요약, 영향, 타임라인, 감지 방법, 원인, 해결, 재발 방지, 배운 점.

**런북** (`docs/runbooks/`): 증상, 확인 순서(명령), 원인별 조치, 에스컬레이션 기준.

**ADR** (`docs/decisions/`): 맥락, 선택지, 결정, 근거, 결과(예: Argo CD vs Flux).

## 8. 작업 규칙

- 브랜치: `feat/<대상>-<주제>` (예: `feat/monitoring-prometheus`, `feat/gitops-argocd`). `main`은 항상 동작하는 상태로 유지하고 PR로 머지한다.
- 커밋: `type(scope): 한글 설명` (기존 규칙). 매니페스트(`feat`)와 문서(`docs`)를 분리해서 커밋한다.
- 각 실습의 **완료 기준**:
  1. 매니페스트·설정이 파일로 저장되어 있고 버전이 고정되어 있다.
  2. 의도한 장애를 일으키고, 감지하고, 복구하는 것까지 직접 확인했다.
  3. 실습 후 클러스터가 파일 기준 상태로 정상화되었다 (`kubectl diff` 비교).
  4. 문서에 결과, 배운 점, 검증하지 않은 것이 구분되어 기록되었다.

## 10. 검토 요청 사항

확정 전에 정해야 할 것들이다.

1. **범위와 우선순위**: 필수/권장/선택 분류가 맞는가? 빼거나 더할 항목이 있는가? (예: 서비스 메시, 멀티 클러스터, 서버리스는 현재 계획에 없음)
2. **GitOps 순서**: Argo CD를 먼저 하고 Flux를 비교하는 순서가 맞는가? 하나만 깊게 할 것인가?
3. **직접 빌드할 앱**: 07번 CI를 위해 간단한 앱(예: 작은 HTTP 서버)을 직접 만들어 이미지로 빌드할 것인가, 아니면 podinfo를 계속 쓰고 CI는 매니페스트 검증 위주로 할 것인가?
4. **클라우드**: 18번에서 실제 클라우드(EKS/GKE)를 쓸 의향이 있는가? 비용 한도와 선호하는 클라우드가 있는가?
5. **로컬 자원**: Docker에 할당된 메모리와 CPU는 얼마인가? (03번 설치 방식을 정하는 데 필요)
6. **언어와 형식**: 문서는 지금처럼 한국어로 작성하는가? 포스트모템과 런북 형식은 7절 그대로 괜찮은가?
7. **진행 방식**: 05번 진단 훈련처럼 제가 문제를 심고 직접 찾는 방식과, 제가 함께 진단하며 진행하는 방식 중 어느 쪽을 원하는가?
